# System Architecture

The ForgeLoop system is designed to treat AI not as a black-box miracle worker, but as an engineering subcontractor. The architecture isolates responsibilities between AI generation, algorithmic evaluation, and human judgment.

## 1. The Core Collaboration Loop

To explicitly enforce that the **AI is not the final authority**, the system is orchestrated around this core loop:

```text
                 ┌──────────────┐
                 │     HUMAN    │
                 │   OBJECTIVE  │
                 └──────┬───────┘
                        ↓
                 ┌──────────────┐
                 │      AI      │
                 │  PROPOSALS   │
                 └──────┬───────┘
                        ↓
                 ┌──────────────┐
                 │    HUMAN     │
                 │    REVIEW    │ (ACCEPT / MODIFY / REJECT)
                 └──────┬───────┘
                        ↓
                 ┌──────────────┐
                 │ EXPERIMENT   │ (BuildArena MCP)
                 └──────┬───────┘
                        ↓
                 ┌──────────────┐
                 │ EVALUATION   │ (Trajectory + Local Scoring)
                 └──────┬───────┘
                        ↓
                 ┌──────────────┐
                 │    HUMAN     │
                 │    DECISION  │ (Decision Ledger)
                 └──────────────┘
```

## 2. Component Architecture

The codebase is split into specific sub-domains to cleanly handle the competition artifacts:

### A. The Data Contract (`src/forgeloop/data/`)
ForgeLoop treats the Kaggle submission files as strict data contracts. 
*   **`machine.py`**: Treats `.bsg` XML files as immutable geometry artifacts. Distinguishes securely between `machine_raw.bsg` (untouched MCP output) and `machine_tuned.bsg` (human-tuned controls).
*   **`trajectory.py`**: Parses the `trajectory.csv` generated by the BuildArena Block Tracker, converting timestamps, positions, velocities, and angular positions into Pandas DataFrames.
*   **`transcript.py` & `history.py`**: Securely handles the `.md` and `.json` artifacts required by the judges to prove MCP origin.

### B. The Score Engine (`src/forgeloop/evaluation/`)
We do not optimize blindly. Every iteration is immediately graded locally against the official Kaggle formula:
*   **Orbit Progress (70%)**: Measures cumulative angular displacement against the 1080-degree (3 orbital period) maximum.
*   **Speed Score (20%)**: Grades `DeltaTheta_eff / ValidFlightTime`.
*   **Structure Integrity (10%)**: Grades the fraction of tracked blocks still attached to the starting block.
*   **Cost Penalty**: Penalizes the length of the system prompt and chat transcript (estimated via `cl100k_base` tiktoken logic).
*   **Final Formula**: `max(0, Performance - 0.20 * Cost) * BuildMode(1.15 or 1.0)`

### C. The Experiment Engine (`src/forgeloop/experiments/`)
Rather than overwriting files manually ("try this model, try that prompt"), ForgeLoop wraps every attempt in an `Experiment` class with a unique ID (e.g., `EXP-014`). This allows us to map specific structural hypotheses to specific score deltas.

### D. The Decision Ledger (`src/forgeloop/decisions/`)
Most AI projects only show what the AI built. ForgeLoop actively tracks what the AI proposed that was **rejected**. 
By maintaining a `DecisionLedger`, we generate an *AI Contribution Report* that mathematically breaks down:
*   Total AI proposals
*   Proposals Accepted
*   Proposals Modified
*   Proposals Rejected 
This mathematically proves the depth of the Human-AI integration.

## 3. Submission Hardening
Before the final Kaggle upload, the `submission.py` module verifies the integrity of the package:
1.  Verifies `machine_raw.bsg` is physically untouched.
2.  Validates that differences between `raw` and `tuned` machines exist solely in legal data fields (e.g., keybinds, spring strength).
3.  Packages the final 6 required files alongside the Writeup and GitHub/YouTube links.
